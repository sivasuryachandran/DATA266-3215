# AI Use - RAG with Reranking, Chunking and Conversational Memory

## What did you use an assistant for, and what did you write yourself?

I wrote most of the implementation myself, including the data loading and preprocessing, the two chunking strategies, ChromaDB indexing and retrieval, reranking, conversational memory, and the evaluation pipeline. I also worked on the queries and evaluation setup based on the assignment requirements.

I mainly used Claude Code for validation and debugging. I used it to review my implementation, check whether I was meeting the assignment requirements, identify edge cases in the chunking and evaluation logic, and verify the outputs after running the pipeline. I also used it to help organize and polish the notebook and report after the main implementation was working.

The numbers reported in the results come from actually running the code rather than values generated by the assistant.

## Give one specific thing it got wrong.

One issue I found during validation was with the sentence-aware chunking logic. The initial approach treated newlines as sentence boundaries, but the dataset stores whole paragraphs or articles on a single line. This resulted in only 100 chunks for strategy 2, essentially one chunk per document, with a mean of 5,686 words and a maximum of 29,688 words. Those chunks were far too large for the embedding model.

After fixing that, I found another edge case where a long section without normal sentence-ending punctuation could still create a chunk of about 1,820 words. I also noticed that my first query set was too easy because reciprocal rank was 1.0 for every configuration, so it was not useful for measuring whether reranking actually helped.

## How did you find out?

I found these problems by checking the statistics and evaluation results produced by my code. The indexing step prints the number of chunks along with the mean, minimum, and maximum chunk sizes. Seeing only 100 chunks for 100 documents, compared with 4,724 chunks using the fixed-window strategy, immediately showed that something was wrong.

After the first fix, the maximum chunk size still exposed the 1,820-word edge case. I also checked the per-query evaluation table and noticed that every query had reciprocal rank 1.0 both with and without reranking. That showed that the original queries were not challenging enough to evaluate the effect of reranking.

## What did you change, and why does your version work now?

I changed the preprocessing so that it detects sentence boundaries using sentence-final punctuation instead of assuming that each line is a sentence. I also added a fallback that splits unusually long sentences into smaller pieces so that malformed text, tables, or reference sections cannot create extremely large chunks.

After the changes, strategy 2 produces 5,256 chunks with a mean of 136 words and a maximum of 300 words, which is much more reasonable and comparable to the fixed-window strategy.

I also added six more challenging paraphrased queries, S9-S14, where the wording is different from the source papers. These queries exposed actual differences between the retrieval configurations. For example, S11 and S14 improved to rank 1 after reranking, while S4 performed worse with sentence-based chunks.

I reran the pipeline after making these changes and used the generated results to verify that the implementation was behaving as expected.
